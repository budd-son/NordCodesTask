# Тест-кейсы

Документ описывает, **что проверяют автотесты и какой результат ожидается**.
Идентификаторы (AUTH-1, TOKEN-5 …) совпадают с названиями тестов в Allure-отчёте.


Тестируется единственный эндпоинт `POST /endpoint` (параметры `token`, `action`, заголовок `X-Api-Key`).
Токен по спецификации — 32 символа `A-Z0-9`. Допустимые действия: `LOGIN`, `ACTION`, `LOGOUT`.


## 1. Защита API-ключом — `AuthorizationTest`

| ID | Что проверяем | Ожидаемый результат |
|----|---------------|---------------------|
| AUTH-1 | Правильный ключ, LOGIN | 200, `result: OK` |
| AUTH-2 | Неверный ключ `wrong_key` | 401, `Missing or invalid API Key` |
| AUTH-3 | Ключ в другом регистре `QAZWSXEDC` | 401, то же сообщение |
| AUTH-4 | Пробел в конце ключа (OWS отбрасывается) | 200, `result: OK` |
| AUTH-5 | Пробел в начале ключа (OWS отбрасывается) | 200, `result: OK` |
| AUTH-6 | Заголовок отсутствует | 401, `Missing or invalid API Key` |
| AUTH-7 | Неверный ключ + неверный токен | 401 — ключ проверяется первым |
| AUTH-8 | Неверный ключ + правильный токен | 401; `/auth` не вызван; сессия не создана (ACTION → 403) |
| INFRA-1 | Запрос содержит ровно один заголовок `X-Api-Key` | 1 значение, без дублей (регрессия на артефакт BUG-002) |

| TOKEN-2 | 33 символа | 400, сообщение о формате |
| TOKEN-3 | 31 символ | 400 |
| TOKEN-4 | Пустая строка | 400 |
| TOKEN-5 | Пробел в конце (всего 32 символа) | 400 |
| TOKEN-6 | Пробел в начале (всего 32 символа) | 400 |
| TOKEN-7 | Кириллическая «Ф» (всего 32 символа) | 400 |
| TOKEN-8 | Строчные буквы | 400 |
| TOKEN-9 | Спецсимвол `_` | 400 |
| TOKEN-10 | Токен не передан | 400, `token: не должно равняться null` |

## 3. Параметр action — `ValidationActionTest`

| ID | Что проверяем | Ожидаемый результат |
|----|---------------|---------------------|
| ACT-1 | LOGIN | 200 |
| ACT-2 | ACTION после LOGIN | 200 |
| ACT-3 | LOGOUT после LOGIN | 200 |
| ACT-4 | action не передан | 400, `action: invalid action 'null'. Allowed: LOGIN, LOGOUT, ACTION` |
| ACT-5 | `login` (строчными) | 400 |
| ACT-6 | `NOTHING` | 400 |
| ACT-7 | Пустая строка | 400 (в сообщении `'null'`) |
| ACT-8  | `" LOGIN"` | Требует решения (OBS-001): «строго» → 400; «мягко» → 200. Сейчас 200. |
| ACT-9 | `"LOGIN "` | Требует решения (OBS-001): «строго» → 400; «мягко» → 200. Сейчас 200. |


## 4. Сессия пользователя — `BusinessLogicTest`

| ID | Что проверяем | Ожидаемый результат |
|----|---------------|---------------------|
| BIZ-1 | LOGIN → ACTION | 200 |
| BIZ-2 | ACTION без LOGIN | 403, `Token '<token>' not found` |
| BIZ-3 | LOGOUT без LOGIN | 403, `Token '<token>' not found` |
| BIZ-4 | LOGIN → ACTION → LOGOUT → ACTION | последний ACTION — 403 |
| BIZ-5 | Повторный LOGIN тем же токеном | 409, `Token '<token>' already exists` |
| BIZ-6 | Двойной LOGOUT | второй — 403 |
| BIZ-7 | LOGIN → ACTION ×3 | все 200 |
| BIZ-8 | Цикл LOGIN → LOGOUT ×3 | все шаги 200 |
| BIZ-9 | Два разных токена | сессии независимы: выход одного не влияет на другого |
| BIZ-10 | Отклонённый повторный LOGIN (409) | исходная сессия жива (ACTION → 200) |

## 5. Взаимодействие с внешним сервисом — `IntegrationWithExternalServerTest`

Внешний сервис замещён WireMock; проверяется число обращений и содержимое запросов.

| ID | Что проверяем | Ожидаемый результат |
|----|---------------|---------------------|
| INT-1 | LOGIN | `/auth` вызван ровно 1 раз |
| INT-2 | Тело запроса к `/auth` | `token=<token>` |
| INT-3 | Заголовки запроса к `/auth` | `Content-Type: application/x-www-form-urlencoded`, `Accept: application/json` |
| INT-4 | LOGIN с невалидным токеном | 400, `/auth` не вызван |
| INT-5 | `/auth` вернул 400/401/403/404/500/503 | LOGIN → 500; токен не сохранён (ACTION → 403) |
| INT-6 | ACTION после LOGIN | `/doAction` вызван ровно 1 раз |
| INT-7 | Тело запроса к `/doAction` | `token=<token>` |
| INT-8 | ACTION без LOGIN | 403, `/doAction` не вызван |
| INT-9 | LOGOUT | `/auth` и `/doAction` не вызваны |
| INT-10 | `/doAction` вернул 500 | ACTION → 500; сессия сохранена (после восстановления ACTION → 200) |

> Поведение INT-5 и INT-10 (код 500, судьба сессии) в спецификации не описано, тесты фиксируют наблюдаемое поведение.
> Эти кейсы стоит уточнить у аналитика.

| ID | Что проверяем | Ожидаемый результат |

| HTTP-1 | `GET /endpoint` | 405 (**сейчас 500**, BUG-004 — требует проверки при живом WireMock) |
| HTTP-2  | `Content-Type: application/json` | 415 или 400 (**сейчас 500**, BUG-004 — требует проверки) |
| HTTP-3  | `POST /unknown` | 404 (**сейчас 500**, BUG-004 — требует проверки) |

| HTTP-5 | Формат ответов | `Content-Type: application/json` у успешного ответа и ответа с ошибкой |
