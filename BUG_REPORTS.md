# Баг-репорты

Дефекты, найденные при тестировании сервиса `internal-0.0.1-SNAPSHOT.jar`.

**Окружение для всех дефектов:** `internal-0.0.1-SNAPSHOT.jar`, запуск
`java -jar -Dsecret=qazWSXedc -Dmock=http://localhost:8888/ internal-0.0.1-SNAPSHOT.jar`,
внешний сервис — WireMock на `:8888` (`/auth` и `/doAction` отвечают 200).

| ID | Кратко                                                                          | Серьёзность | Приоритет | Статус |
|----|---------------------------------------------------------------------------------|-------------|-----------|--------|
| [BUG-001](#bug-001) | Токен принимается только из символов 0-9A-F, а по спецификации допустимо A-Z0-9 | Critical | High | Открыт |
| [BUG-004](#bug-004) | Неверный метод / Content-Type / путь дают 500 вместо 405 / 415 / 404            | Minor | Low | Требует проверки |

> **История изменений:**
> - **BUG-002** (ключ `X-Api-Key` с пробелом → 500) — **закрыт как артефакт теста**.
    >   Причина: в старой версии `AuthorizationTest` заголовок `X-Api-Key` добавлялся поверх
    >   заголовка из глобальной спецификации, и на сервер уходили **два** заголовка одновременно.
    >   После исправления (заголовок один) пробелы по краям значения отбрасываются HTTP-клиентом/сервером
    >   (RFC 7230 §3.2.4 OWS; в RFC 9110 зафиксировано явно), ключ остаётся валидным → `200`.
    >   Дефекта приложения нет. Тесты AUTH-4/5 переведены в позитивные (ожидают `200`).
> - **BUG-003** (`action` с пробелами принимается) — **понижен до наблюдения**.
    >   Трим `action` — не дефект сам по себе; расхождение с `token` (где пробелы отклоняются)
    >   требует решения аналитика: «строго» (поправить приложение) или «мягко» (поправить документацию).
    >   Пока не подтверждено как баг — не включён в таблицу дефектов.

## BUG-001

**Заголовок:** Приложение отклоняет токены с буквами G–Z, хотя по спецификации они допустимы

**Серьёзность:** Critical  
**Приоритет:** High  
**Статус:** Открыт

**Описание.** В документации токен описан как «строка длиной 32 символа, состоящая только из символов A-Z0-9».
Приложение проверяет токен регулярным выражением `^[0-9A-F]{32}$`, то есть считает допустимыми только шестнадцатеричные символы.
Из 36 допустимых по спецификации символов приложение принимает только 16.


**Шаги воспроизведения.**
1. Запустить приложение (см. окружение выше).
2. Выполнить:
```bash
curl.exe -i -X POST http://localhost:8080/endpoint -d "token=GGGGGGGGGGGGGGGGGGGGGGGGGGGGGGGG&action=LOGIN" -H "X-Api-Key: qazWSXedc" -H "Accept: application/json" -H "Content-Type: application/x-www-form-urlencoded"
```
3. Повторить с токеном `ZZZZZZZZZZZZZZZZZZZZZZZZZZZZZZZZ` и с `0123456789ABCDEFGHIJKLMNOPQRSTUV`.

**Ожидаемый результат.**
Токен соответствует спецификации (32 символа, A-Z0-9) → проверка формата пройдена. При работающем внешнем сервисе: `HTTP 200`, `{"result":"OK"}`.

**Фактический результат.**
`HTTP 400`
```json
{"result":"ERROR","message":"token: должно соответствовать \"^[0-9A-F]{32}$\""}
```
Текст ошибки сам показывает, что в проверке зашит набор `0-9A-F`.

**Что неясно / как трактовать.**
Возможны два варианта: ошибка в коде (регулярку нужно заменить на `^[0-9A-Z]{32}$`) либо ошибка в документации (на самом деле токен — это hex). Нужно подтвердить у аналитика/разработчика. Тесты написаны по документации, поэтому до уточнения считаем дефектом приложения.

**Связанные тесты:** `ValidationTokenTest` — TOKEN-12a, TOKEN-12b, TOKEN-12c (падают).

## BUG-004

**Заголовок:** Некорректные HTTP-запросы приводят к 500 вместо 405 / 415 / 404

**Серьёзность:** Minor  
**Приоритет:** Low  
**Статус:** Требует проверки

**Шаги воспроизведения.**
```bash
# 1. неверный метод
curl -i -X GET http://localhost:8080/endpoint -H "X-Api-Key: qazWSXedc"

# 2. неверный Content-Type
curl -i -X POST http://localhost:8080/endpoint -H "X-Api-Key: qazWSXedc" \
  -H "Content-Type: application/json" \
  -d '{"token":"A1B2C3D4E5F6A1B2C3D4E5F6A1B2C3D4","action":"LOGIN"}'

# 3. несуществующий путь
curl -i -X POST http://localhost:8080/unknown -H "X-Api-Key: qazWSXedc" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "token=A1B2C3D4E5F6A1B2C3D4E5F6A1B2C3D4&action=LOGIN"
```

**Ожидаемый результат.**
1 — `405 Method Not Allowed`; 2 — `415 Unsupported Media Type` (допустимо 400); 3 — `404 Not Found`.

**Фактический результат.**
Во всех трёх случаях `HTTP 500`.

**Важное замечание (проверить перед подтверждением).**
`500` в этих кейсах может быть **следствием недоступности WireMock на `:8888`** (приложение при любом запросе сначала ходит во внешний сервис, а при `Connection refused` конвертирует это в `500`).
Перед подтверждением BUG-004 необходимо:
1. Поднять WireMock на `:8888` и застабить `/auth` и `/doAction` на `200`.
2. Повторить все три `curl` — если ответы станут `405` / `415` / `404`, значит дефекта нет (это был артефакт окружения).
3. Если и при живом WireMock приходит `500` — дефект подтверждён.

**Связанные тесты:** `HttpLevelTest` — HTTP-1, HTTP-2, HTTP-3.

## Наблюдения (не дефекты, требуют решения аналитика)

### OBS-001. `action` с пробелами по краям принимается (`trim`), `token` — отклоняется

**Серьёзность:** — (наблюдение)  
**Приоритет:** —  
**Статус:** Требует уточнения

**Описание.**
Приложение молча обрезает пробелы по краям значения `action` (`" LOGIN"`, `"LOGIN "` → выполняет LOGIN, отвечает `200`), тогда как для `token` пробелы приводят к `400` (строгий regex `^[0-9A-F]{32}$`). В спецификации обработка пробелов в `action` не описана, поэтому трактовать как баг нельзя.

**Шаги воспроизведения.**
```bash
curl -i -X POST http://localhost:8080/endpoint \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -H "Accept: application/json" \
  -H "X-Api-Key: qazWSXedc" \
  --data-urlencode "token=A1B2C3D4E5F6A1B2C3D4E5F6A1B2C3D4" \
  --data-urlencode "action= LOGIN"
```

**Ожидаемый результат (по строгой трактовке).**
`400`, `action: invalid action ' LOGIN'. Allowed: LOGIN, LOGOUT, ACTION`.

**Фактический результат.**
`200`, `{"result":"OK"}` — пробелы обрезаны, действие выполнено.

**Что нужно решить.**
- **Вариант «строго»:** приложение не должно тримить `action` → баг в приложении (тогда это BUG-005, Minor/Low).
- **Вариант «мягко»:** трим — осознанное поведение, документация должна явно это описывать → тесты ACT-8/9 переписать в позитивные (ожидать `200`).

**Связанные тесты:** `ValidationActionTest` — ACT-8, ACT-9 (в текущей версии ожидают `400`; судьба зависит от решения).

> Примечание: ранее это было оформлено как BUG-003. Понижено до наблюдения, так как не подтверждено, что это дефект, а не задуманное поведение. Упоминание BUG-003 из Allure-тегов и тест-кейсов убрано.

## Закрытые / снятые дефекты

### BUG-002 (закрыт как артефакт теста)

**Заголовок (исходный):** Заголовок `X-Api-Key` с пробелом в начале или конце приводит к 500 вместо 401.

**Причина закрытия.**
В старой версии `AuthorizationTest` метод `apiWithKey(key)` добавлял `.header("X-Api-Key", key)` **поверх** заголовка из глобальной `RequestSpecification`, где уже был `X-Api-Key: qazWSXedc`. На сервер уходили **два** заголовка `X-Api-Key` одновременно. Приложение, читая заголовки, получало неожиданную комбинацию и отвечало `500` — это был дефект **теста**, а не приложения.

**После исправления.**
Заголовок один. Пробелы по краям значения (OWS) отбрасываются HTTP-клиентом/сервером (RFC 7230 §3.2.4, «ought to»; в RFC 9110 зафиксировано явно). Ключ остаётся валидным → `200`.

**Что изменено в тестах.**
- AUTH-4, AUTH-5 переименованы (`keyWithSurroundingWhitespaceAccepted`) и ожидают `200` вместо `401`.
- Убраны `@Issue("BUG-002")` и `@Tag("known-bug")`.
- Добавлен регрессионный тест `INFRA-1` (ровно один заголовок `X-Api-Key` в запросе), чтобы артефакт не вернулся.
